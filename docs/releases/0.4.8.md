# Listener 0.4.8

自动衔接完成时的顿挫已定位到 `playbackRate` 变化，改为原速交叉淡化。

## Root Cause

0.4.7 诊断版记录了一次真实衔接：

- QQ 方案速率：`1.226660`
- 过渡时长：`5.4375 s`
- 旧音源 `pause` / `load` / 断开节点：均 `0 ms`
- `finish()` 总耗时：`1 ms`
- `mixMode` 清空 + `nextTick`：`1 ms`
- 下一首音源请求：`565 ms`，异步，期间帧间隔正常

在 `playbackRate` 从 `1.226660` 改为 `1` 后，紧接着出现一帧 **98 ms** 的间隔，下一首的 `currentTime` 同期停滞；没有 `waiting`、`pause`、`error` 事件，`readyState` 为 4。说明不是网络、解码或旧音源释放，而是 WebKit 在播放中重配“保持音高”的变速管线。

0.4.5 连续 30 次修改 `playbackRate` 会反复触发该重配，因此从一次顿挫升级为持续卡死。

## Modified Scope

- `player.ts`：衔接时不再把下一首设为 QQ 的速率；`plan.input`、`plan.out`、淡化时长和滤波曲线保留，但音源始终以 `1.0` 播放。
- 交叉淡化时长限制在下一首剩余音频内，避免原速播放越过音频末尾。
- `qq-automix.ts`：只在与 `1` 不同时设置 `playbackRate`，避免无意义的重复赋值。
- `SettingsPanel.vue`：说明改为“按 QQ 音乐的切点交叉淡化下一首，不改变播放速度”。
- `tests/player.test.ts`：更新为验证传入 fade 的速率是 `1`，下一首 `playbackRate` 保持 `1`。

## Tradeoff

不再做 QQ 的 BPM 节拍匹配；不同速歌曲的衔接以切点和滤波淡化为准，节奏可能不完全对齐，但切点不再触发变速停顿。若要同时保留节拍匹配和无停顿，需要独立的 AudioWorklet time-stretch 实现。
